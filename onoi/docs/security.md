# Безопасность: что проверено и как реализовано

| Область | Реализация |
|---|---|
| Секреты | только `.env` (600) — `SECRET_KEY`, `JWT_SECRET`, `SESSION_SECRET`, `WEBHOOK_SECRET`, `ENCRYPTION_KEY`, токены ботов, SMTP, VAPID. В production сервер не стартует без секретов ≥32 символов. Старые секреты LUXON не переносятся (`legacy_import` копирует только учётные данные касс и QR-реквизиты). |
| Учётные данные касс | шифруются в БД AES-256-GCM (`ENCRYPTION_KEY`), в API отдаются только маской. |
| Пароли админов | Argon2id (`argon2-cffi`), политика: ≥10 символов, регистр, цифра. |
| Сессии | opaque-токен в cookie `HttpOnly; Secure; SameSite=Strict; Path=/onoipay/`; в БД хранится только SHA-256 хэш; скользящее продление (`SESSION_IDLE_DAYS=14`) + абсолютный срок (`SESSION_ABSOLUTE_DAYS=60`) — администратор не разлогинивается каждые 14 дней при активной работе, при этом любая сессия отзываема. Ротация токена `/api/auth/refresh` (старый токен живёт 2 минуты для параллельных вкладок). |
| Просмотр/отзыв сессий | `/api/auth/sessions`, revoke по id, «завершить остальные», принудительный logout любого админа владельцем, автоматический отзыв при смене пароля/деактивации. |
| JWT | только короткоживущие (15 мин) bearer-токены для скриптов по запросу `/api/auth/token`; никогда не попадают в URL; привязаны к сессии (отзыв сессии = отзыв токена). |
| CSRF | double-submit: cookie `onoipay_csrf` + заголовок `X-CSRF-Token` обязательны для всех cookie-запросов, меняющих состояние. |
| Brute force | лимит попыток по IP и по логину (`LOGIN_MAX_ATTEMPTS=5`, блокировка `LOGIN_LOCK_MINUTES=15`) в БД + `limit_req` в nginx на `/api/auth/login`. |
| RBAC | роли viewer/operator/admin/owner, проверка `require(<permission>)` на каждом роуте; критичные действия (кассы, настройки, админы) недоступны оператору. |
| Audit log | `audit_logs`: вход/выход, неудачные входы, действия с заявками, кассами, настройками, пользователями, сессиями (кто, что, IP, детали). |
| XSS | фронтенд строит DOM через `createElement`/`textContent`, `innerHTML` не используется для пользовательских данных; CSP `default-src 'self'`, `frame-ancestors 'none'`. |
| SQL injection | только SQLAlchemy с параметризованными запросами. |
| SSRF | сервер загружает только файлы Telegram (`api.telegram.org`) и фото по URL заявки для оператора; произвольные URL от пользователей не запрашиваются. |
| IDOR | все объекты выдаются только авторизованным админам; клиентские ссылки (QR пополнения) используют неугадываемый `public_id`; бот проверяет `user_id` владельца заявки/QR. |
| Cookies/CORS | CORS не включён (same-origin), `Secure` за HTTPS-прокси через `X-Forwarded-Proto`. |
| Security headers | HSTS, `X-Frame-Options: DENY`, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, CSP, `Cache-Control: no-store` для API. |
| Webhook платежей | секрет в пути или `X-Webhook-Key` (константное сравнение) либо подпись `X-Signature = HMAC-SHA256(body, WEBHOOK_SECRET)`; идемпотентность по `event_key`; лимит частоты в nginx. |
| Telegram | боты работают по long polling: входящих webhook-эндпоинтов Telegram нет, атака подменой webhook невозможна; токены только в `.env`; загрузки клиентов сохраняются локально с хэш-именами. |
| Rate limiting поддержки | антифлуд на уровне сервиса (окно/лимит/cooldown, подавление повторов, cooldown эскалаций). |
| Session fixation | новый токен сессии выдаётся только после успешной аутентификации; старые не переиспользуются. |
| Логи | секреты и токены в логи не пишутся; учётные данные касс маскируются. |

Рекомендации по эксплуатации: держать `.env` с правами 600, включить автоматические бэкапы, ограничить доступ к PostgreSQL localhost, регулярно проверять `audit_logs` и раздел «Безопасность → Активные сессии».
